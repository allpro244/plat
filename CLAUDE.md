# A VISUAL CLAIM WITHOUT A RENDERED IMAGE IS NOT A CLAIM

**Never say a thing looks right until you have rendered it and looked at it.**

This is the first rule because it is the one that will be broken most often and
because its cost is invisible. Shader code compiles and runs while producing
something nobody would ship. A material can be physically wrong in a way that
only shows at one sun angle. A building grammar can generate forty plausible
towers and one that intersects itself, and the one is the one in the
screenshot. None of that is caught by a type check or a unit test.

So every change that touches how something looks ends with a render, and the
render is attached to the commit. `tools/shoot.*` exists for exactly this, it
runs headless, and it is cheap. Use it constantly.

This rule is inherited, and it was learned expensively. The predecessor project
spent three commits and a full investigation chasing seven months of a broken
ledger that did not exist, because every probe was loading a bundle nineteen
hours stale — and the obvious control confirmed the wrong conclusion, because
both sides of it loaded the same stale bundle. Assume your instrument is lying
until you have made it prove otherwise.

# THE CAMERA CONTRACT IS LOAD-BEARING

The camera is **orbital and constrained to defined height bands.** It is not a
preference and it is not a placeholder. It is the single decision that every
other decision in this repository derives from:

- Interiors are never rendered, so buildings are shells.
- Facade detail is authored for the closest band and impostored beyond it.
- Ambient occlusion and contact shadows can be baked, because the relationship
  between geometry and ground does not change per frame.
- Street-level prop density can be an impression rather than an inventory.
- Silhouette and roofscape matter more than doorways, because the closest band
  still looks *down*.

Every one of those is a large saving, and every one of them is void the moment
somebody adds a free-fly camera "just for screenshots". If the contract ever
needs to change, that is a design decision with a cost estimate attached, not a
convenience. Write down what it would break before proposing it.

# THE SIM OWNS QUANTITIES. THE RENDERER OWNS FORM.

The simulation says: *180,000 square feet, 62% office, 14 floors, built 1928,
71% let, condition 0.44, one crane on site, sixteen months to delivery.*

The renderer decides what that **looks like** — the massing, the setbacks, the
bay rhythm, the material, the window pattern, which floors are lit at dusk.

This line is the whole architecture. Hold it and either half can be rewritten
without touching the other; the simulation stays headless and testable from a
command line, and the renderer can be swapped for a better one in two years.
Break it — let the sim start dictating shapes, or let the renderer start
deriving economics — and you have one program that is bad at both jobs, which
is the failure mode that has sunk larger city games than this one.

The practical test: **the simulation must run, and pass all of its own tests,
with the renderer deleted.**

# PROCEDURAL, NOT HAND-AUTHORED

There is no asset kit and there are no hand-modelled buildings. Variety is a
code problem with a seed on it.

Buildings are generated by a shape grammar working from the parcel: extrude the
lot, apply era-appropriate street-wall and setback rules, then dress the facade
from a vocabulary of bays, spandrels, cornices, glazing ratios and ground-floor
conditions. A 1928 masonry loft and a 1974 curtain-wall slab differ because
their *rules* differ, not because somebody modelled two buildings.

Materials come from CC0 scan libraries — Poly Haven, ambientCG — fetched by
script, no account, no licence to track. These are the same tier of data
commercial games use, and they are the reason this project can look expensive
without an art team. `tools/fetch-assets.*` owns that, and what it pulls is
pinned so a render is reproducible.

# DETERMINISM IS A TEST INSTRUMENT, NOT A NICETY

Same seed, same camera, same date and time of day, same image. Every time.

That property is what makes the graphics testable at all, and it buys the
direct analogue of the predecessor's `BASELINE.json`: a set of committed
reference renders that every build reproduces and diffs against. Movement is
not failure — a change that improves the world moves pixels, and that is the
point. What it is for is **making sure nobody moves one without noticing.**

The predecessor learned this the hard way: the median land value in that city
fell 71% in a single commit with every check in the repo green, because nothing
was shaped to notice a number that was simply wrong. A city can be quietly,
uniformly wrong-looking in exactly the same way, and no assertion about frame
time or triangle count will see it.

So: pin the seeds, pin the camera, pin the sun, commit the references,
regenerate deliberately, and say in the commit message why the picture changed.

# NO FAKE FRAMES

The predecessor's standard was that no number in the economy may be a
constant chosen to make an outcome come out right. The same standard applies
here, to appearance.

A building looks weathered because its condition index is low, not because
grime was painted on uniformly. A window is dark because that floor is not let.
A street is busy at noon and empty at midnight because the employment model
says so. A block reads as declining because its shopfronts are actually vacant
in the simulation.

The temptation will be to fake these, because faking them is faster and looks
the same in a screenshot. It does not look the same in *motion*, over a
century, and it forfeits the only real advantage this project has over a
prettier game: that the city means something. A post-process that hides a wrong
model is the graphics equivalent of a coefficient that exists because the
median run looked wrong without it.

Calibrated physical constants are the opposite of fakes and belong hardcoded
with a comment saying where they come from — a real sun position for a real
latitude, a measured albedo, a physically-based exposure. The test is not "is
it a constant", it is **"is it a fact about the world, or a thumb on the
scale."**

# WHAT THIS PROJECT INHERITS AND WHAT IT DOES NOT

It inherits the *discipline* of `broadway-and-wall`: measure before claiming,
adversarial harnesses, comments that carry their measurements, and a refusal to
make a thing hard or pretty by decree instead of by mechanism.

It does not inherit that repository's code, its build commands, or its test
names. `pnpm gate`, `pnpm conserve` and `BASELINE.json` belong to a program
that is not this one. When the economy is ported, its harnesses come with it
and they will be named here.
